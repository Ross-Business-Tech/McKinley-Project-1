# Render (backend)

**Status (2026-11-11): deployed as a public demo, `https://mckinley-backend.onrender.com` (free web service
`srv-dbpr730ae00c73cdsl80`, Oregon, branch `development`, auto-deploy on commit).** Replies from OpenRouter
(`nvidia/nemotron-3.5-super-vl:free`), data in the team's **development** Supabase project (synthetic only).
Prototype, not production. The website is a Render static site: [render-frontend.md](render-frontend.md).

- Build: `pip install uv && env -u UV_NO_MANAGED_PYTHON uv sync --frozen --no-dev` (reproducible from
  `backend/uv.lock`; the `env -u` matches the live service, set in the Dashboard after the first Blueprint build failed).
- Start: `alembic upgrade head` then `uvicorn app.main:app --host 0.0.0.0 --port $PORT` (one process).
- Health: `GET /api/health` → `status`, provider/model, `provider_ready`, `is_mock`, `app_env`. On `APP_ENV=hosted`
  the database kind and resident counts are **hidden** from the public (empty / 0); the startup log shows them.
- `APP_ENV=hosted`: the app **refuses to start** with wildcard/localhost/http CORS origins, a missing or short
  `STAFF_API_TOKEN`, `GATE_OVERRIDE_ENABLED=true`, `QUICKFIX_CONTENT_MODE=demo_drafts`, `DEMO_PERSONAS_ENABLED`
  or no `DATABASE_URL`. Messages never print values.
- Postgres connections **require TLS** for any non-local host unless the URL sets `sslmode` (`app/db.py`
  `pg_tls_args`; psycopg's default would silently fall back to plaintext).

## Errors the public sees
A model failure never shows the provider's own text (it can name settings or addresses). Customers get
`ASSISTANT_BUSY` ("busy right now", retry; rate limit, timeout, provider down) or `ASSISTANT_UNAVAILABLE` ("not
available", contact the office; missing or rejected key, unknown model), HTTP 503. Callers with the staff token
get the original code (`NEEDS_API_KEY`, `MODEL_RATE_LIMITED`, …). Many model errors never reach anyone: when the
planner has approved wording for the turn, that wording is used and labelled `template_after_model_error`.

## Incident 2026-11-11: chat returned 503
`POST /api/chat` → `503 {"error": {"code": "NEEDS_API_KEY", …}}` and every start logged `default provider
openrouter is not ready (NEEDS_API_KEY)`. Cause: `OPENROUTER_API_KEY` was not set on the service (the database,
cold start and timeouts were fine). Fix: the key was added on the Environment page; `/api/health` then showed
`provider_ready: true`. The customer error text was also made safe (above).

Limitations: the free plan sleeps after ~15 minutes idle (first request ≈1 minute); the in-memory lock means one
instance only; staff and evaluation routes are closed to browsers (they need the `X-Staff-Token` header, which the
website never sends) until there is real staff sign-in; there is no customer authentication, so the public site
is guest-only.
